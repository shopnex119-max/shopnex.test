# SHOPNEX ULTIMATE

نظام أعمال مكتبي محلي قيد التطوير، ببنية **Tauri + React/TypeScript + FastAPI + PostgreSQL**، وواجهة عربية RTL بطابع مستقبلي. هذه النسخة تشمل واجهة لوحة قيادة ووحدات أساسية أولية وشاشة إعداد ZATCA؛ بيانات اللوحة والجداول المعلّمة بأنها تجريبية ليست سجلات أعمال فعلية.

> **تنبيه زاتكا:** لا يوجد في هذه النسخة إرسال فعلي إلى ZATCA/FATOORA، ولا تدّعي اعتمادًا رسميًا. شاشة الإعداد تحفظ بيانات المنشأة محليًا وتتحقق محليًا فقط. إدخال مفتاح الربط لا يعني الاتصال بالجهة؛ يجب مطابقة كل اعتماد وشهادة وواجهة ونوع إرسال مع أحدث وثائق الجهة وإتمام Sandbox من حساب المكلف قبل أي تفعيل إنتاجي.

## تنزيل نسخة Windows للتجربة

حزمة Windows x64 الكاملة، بما فيها المُثبت وسكربت التثبيت بنقرة مزدوجة، متاحة من [صفحة الإصدارات على GitHub](https://github.com/shopnex119-max/shopnex.test/releases/latest).

يمكنك [فتح المعاينة العامة في المتصفح](https://shopnex119-max.github.io/shopnex.test/). تستخدم بيانات توضيحية فقط، ولا تحفظ سجلات أو تتصل بخدمة API أو زاتكا.

## المتطلبات

- Node.js 22 وpnpm 10/11
- Python 3.12
- Rust toolchain + متطلبات Tauri للنظام المستهدف عند تشغيل تطبيق سطح المكتب
- PostgreSQL 16 للتشغيل المعبأ عبر Docker Compose (Docker غير مطلوب لتشغيل تطوير SQLite المحلي)

## التشغيل التطويري (واجهة وخدمة محلية)

من جذر المستودع:

```bash
pnpm install
python3 -m venv services/api/.venv
source services/api/.venv/bin/activate
python -m pip install -r services/api/requirements.txt
```

شغّل في طرفية أولى؛ يهيئ السكربت SQLite التطويرية بالترحيلات ويولّد سر جلسة محليًا إذا لم يوجد ملف `.env`:

```bash
bash scripts/run-api.sh
```

على Windows يمكن تشغيل خدمة API من PowerShell بواسطة `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-api.ps1`.

وفي طرفية ثانية من جذر المشروع:

```bash
pnpm dev
```

واجهة التطوير: `http://127.0.0.1:1420`، ومرجع API: `http://127.0.0.1:8000/docs`. عند أول تشغيل مكتبي، أنشئ حساب المالك بكلمة مرور قوية (١٢ حرفًا فأكثر). التشغيل الافتراضي يستخدم SQLite محليًا للتجربة؛ يوصى بقاعدة PostgreSQL محلية للاستخدام التشغيلي.

## تشغيل Tauri

أولاً شغّل API المحلية. ثم:

```bash
pnpm desktop:dev
```

لبناء حزمة Debian/Ubuntu على Linux x86_64 (بعد تثبيت متطلبات Tauri):

```bash
pnpm desktop:build
```

الناتج `.deb` خاص بـLinux ولا يضمّن FastAPI؛ شغّل `bash scripts/run-api.sh` أولًا كما في القسم السابق. توجد حزمة Windows x64 منفصلة تتضمن مُثبت الواجهة وخدمة API المحلية وسكربت تثبيت بنقرة مزدوجة. لم تُنشأ حزمة macOS، ولا تتضمن أي حزمة اعتمادًا أو سرًا حقيقيًا من ZATCA.

## PostgreSQL محلي عبر Docker Compose

للاستفادة من خزنة أسرار نظام التشغيل، يشغّل FastAPI على الجهاز المضيف؛ شغّل PostgreSQL محليًا عبر Docker Compose (لا تضع اعتماد ZATCA داخل حاوية API):

```bash
docker compose --env-file .env -f infra/docker-compose.yml up -d postgres
```

قبل ذلك انسخ `.env.example` إلى `.env` وغيّر `POSTGRES_PASSWORD` و`DATABASE_URL`. منفذ PostgreSQL مربوط بـ`127.0.0.1` فقط. لا تفتح قاعدة البيانات أو API على شبكة عامة. بيانات PostgreSQL دائمة في volume محلي `shopnex-postgres`.

## API الحالية

- `GET /api/health` — فحص عملية API وقاعدة البيانات.
- `GET /api/v1/zatca/config?environment=sandbox|production` — بيانات الإعداد العامة وحالة وجود الاعتماد دون إرجاع قيمته.
- `PUT /api/v1/zatca/config` — حفظ بيانات المنشأة؛ الاعتماد اختياري ويُمرر إلى خزنة النظام ولا يُعاد للعميل.
- `POST /api/v1/zatca/validate` — تحقق محلي للحقول فقط، ولا يرسل طلبًا للجهة.
- `POST /api/v1/zatca/test-connection` — متوقف عمدًا حتى تجهيز محول مطابق للوثائق الرسمية.
- `GET/POST /api/v1/products` — كتالوج محلي للسعر ومعدل الضريبة وكمية الرصيد، مع خيار تسجيل السعر شاملًا للضريبة.
- `GET/POST /api/v1/invoices` — إنشاء الفواتير بمعرّفات أصناف الكتالوج؛ يعيد الخادم حساب البنود والخصم والضريبة، ويحفظ تفاصيل البنود والمدفوعات وحركات المخزون داخل معاملة واحدة. تدفق البيع المطوّر غير منشور بعد، وتبقى التغطية المحاسبية الشاملة ضمن خارطة الطريق.
- `GET/POST /api/v1/modules/{restaurant|crm|hr}/records` و`PUT/DELETE /api/v1/modules/{restaurant|crm|hr}/records/{id}` — سجلات محلية محمية للمطاعم/الطاولات، والعملاء/نقاط الولاء، ودليل الموظفين.

## الوحدات المفعّلة في الإصدار 0.2.0

- **المطاعم والمطبخ:** إضافة الطلبات والطاولات، متابعة الطلبات عبر حالات جديد/تحضير/جاهز/مكتمل، وتحديث إشغال الطاولة.
- **CRM والولاء:** دليل العملاء، شرائح العملاء، وإضافة 10 نقاط ولاء بضغطة واحدة.
- **الموظفون والموارد البشرية:** دليل أساسي للموظفين، أقسامهم وحالة العمل أو الإجازة.

تُحفظ تغييرات الجلسة المسجّلة في قاعدة البيانات المحلية بعد ترقية المخطط تلقائيًا عند تشغيل `scripts/run-api.sh`. في **وضع العرض التجريبي** تكون التعديلات مؤقتة ولا تُحفظ. الوحدات لا تشمل حاليًا الرواتب أو الحضور أو تصدير كشوف رسمية أو إدارة مطاعم متكاملة.

توجد خطوات استبدال وحفظ البيانات في [`UPDATE-AR.md`](UPDATE-AR.md).

## دفعة التطوير غير المنشورة

يجري العمل محليًا على شاشة كاشير محسنة، شاشة مطبخ، شاشة قائمة/طلب للضيف، ومحرك مالي أدق. التفاصيل والحدود واختبارات الدفعة في [`docs/STATUS.md`](docs/STATUS.md) وخارطة التنفيذ في [`docs/IMPLEMENTATION-ROADMAP.md`](docs/IMPLEMENTATION-ROADMAP.md). معاينة الضيف لا ترسل طلبات حقيقية، ولا تمثل النسخة نظام ERP مكتملًا أو تكاملًا فعليًا مع ZATCA.

تتضمن حزمة الإصدار الكاملة على Linux سكربت `update-shopnex-0.2.0.sh`. ضعه في جذر مجلد المشروع القديم وشغّله من Terminal بـ`bash update-shopnex-0.2.0.sh`؛ يحفظ `.env` ومفتاح الأسرار وملف SQLite المحلي إذا أمكن تحديده، ينسخ الملفات المحدّثة دون حذف البيانات، يثبت واجهة Debian/Ubuntu ويطبق ترحيل قاعدة البيانات. يحتاج `sudo`، ولا يحذف ملفات المشروع القديمة.

على Windows استخدم الحزمة التي تنتهي بـ`Windows.zip`، وفك ضغطها بالكامل، ثم اضغط مرتين على `INSTALL-SHOPNEX-WINDOWS.bat`. لا تستخدم `.deb` أو ملف `.sh`. راجع [`UPDATE-WINDOWS.md`](UPDATE-WINDOWS.md)؛ ينشئ المثبّت نسخة احتياطية عند تحديث مشروع قائم، ويجهز اختصار سطح المكتب لتشغيل البرنامج والـAPI.

## الأسرار وحماية البيانات

- لا تضع مفاتيح حقيقية أو ملفات شهادات أو `.env` في Git أو محادثة أو لقطة شاشة.
- أسرار ZATCA لا تُعاد من API ولا تُخزّن في LocalStorage. عند إدخال اعتماد، يحتاج الحفظ إلى خزنة نظام تشغيل متاحة عبر `keyring`; عند تعذرها يرفض الخادم حفظ السر بدل تخزينه نصًا صريحًا.
- ملفات الشهادة والمفتاح الخاص تبقى في مسارات محلية مقيدة الوصول، ولا تُرسل إلى هذه الواجهة. لا تنفذ إدخال المفتاح الخاص في ملف عام أو مستودع.
